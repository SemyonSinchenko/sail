# Graph500-generated traversal inputs

This prepares weighted Graph500 inputs for the Sail traversal benchmark. It
streams the pinned upstream generator directly into partitioned Parquet, without
retaining the graph or a second raw edge file in memory or on disk. It preserves
the generated edge order, self-loops and duplicates, and includes every vertex ID
from `0` to `2^scale - 1`, including isolates.

This is input preparation, **not an official Graph500 benchmark result**. Root
sampling, parent-tree verification, the timed regions and TEPS reporting still
need separate qualification against the [Graph500 specification](https://graph500.org/?page_id=12).
The harness defaults to independent reference distances. An explicit
`--traversal-validation certificate` instead checks all-edge distance inequalities
and source-rooted reachability through tight edges using distributed queries.
This includes disconnected zero-weight cycles, which local inequalities alone
cannot reject. It records a conservative accumulated absolute-error bound for
floating-point SSSP; it is not a full-vector reference comparison. Certificate
work and its round cap are outside timing, and incomplete validation is failure.
No large input is qualified merely by successful preparation.

## Build the pinned generator

Run from the Sail checkout. Use a separate directory for generated binaries and
fixtures so the measured source checkout remains clean. A C11 compiler, Git,
Python 3.10+ and a Python environment with NumPy and PyArrow are required.

```bash
export GRAPH500_WORK="$HOME/sail-graph500"
mkdir -p "$GRAPH500_WORK"
git clone https://github.com/graph500/graph500.git "$GRAPH500_WORK/upstream"
git -C "$GRAPH500_WORK/upstream" checkout --detach f89d643ce4aaae9a823d310c6ab2dd10e3d2982c
python3 -m venv "$GRAPH500_WORK/venv"
"$GRAPH500_WORK/venv/bin/python" -m pip install numpy pyarrow pytest

bash examples/extensions/benchmarks/traversal-controls/build_graph500.sh \
  "$GRAPH500_WORK/upstream" "$GRAPH500_WORK/graph500_stream"
```

The builder rejects an upstream checkout with a different commit or tracked
modifications. The small adapter calls the upstream `generate_kronecker_range`
with `SSSP` enabled; it contains no replacement random graph generator. The
sidecar `graph500_stream.build.json` records the source files, adapter and binary
hashes, compiler, arguments and build host. Preserve it with the binary. The
preparer verifies the binary and adapter hashes before running it.

The default build is serial. On Linux with GCC/OpenMP available, build an
explicitly parallel binary and choose its preparation thread count:

```bash
CC=gcc CFLAGS='-O3 -fopenmp' \
  bash examples/extensions/benchmarks/traversal-controls/build_graph500.sh \
  "$GRAPH500_WORK/upstream" "$GRAPH500_WORK/graph500_stream-openmp"
export OMP_NUM_THREADS=16
```

Keep preparation outside all measured trials. Do not run it concurrently with a
benchmark on the same host. On macOS, use a compiler and OpenMP installation
that support these flags, or keep the default serial build.

## Start with a correctness fixture

```bash
"$GRAPH500_WORK/venv/bin/python" examples/extensions/benchmarks/graph500_fixture.py \
  --generator "$GRAPH500_WORK/graph500_stream" \
  --output "$GRAPH500_WORK/scale10" \
  --scale 10 --edge-factor 16 --seed1 42 --seed2 54 \
  --source 0 --no-directed --reference
```

This generates 1,024 vertices and 16,384 edge tuples, plus independent deque-BFS
and heap-Dijkstra reference distances. The fixture is interpreted as undirected
by default, while each original tuple is stored once. Use `--directed` to test a
directed interpretation; it changes the traversal contract and references, not
the generated bytes. Source `0` is an explicit fixed choice, not Graph500 root
sampling; it can be isolated.

Weights are the upstream generator's `float32` values widened exactly to
`float64`, without quantization, rescaling or replacement. Both endpoints and
weights are checked as each chunk arrives. A request for `--reference` above
100,000 vertices or 1,000,000 edges fails before launching the generator: the
Python oracle is deliberately restricted to small graphs.

## Prepare a capacity input

After small correctness tests, select a scale that fits the planned execution
envelope. The number of tuples is `edge_factor * 2^scale`.

```bash
"$GRAPH500_WORK/venv/bin/python" examples/extensions/benchmarks/graph500_fixture.py \
  --generator "$GRAPH500_WORK/graph500_stream" \
  --output "$GRAPH500_WORK/scale24" \
  --scale 24 --edge-factor 16 --seed1 42 --seed2 54 \
  --source 0 --no-directed --chunk-edges 262144 --chunk-vertices 262144
```

| Scale | Vertices | Generated edge tuples | Uncompressed edge records |
| --- | ---: | ---: | ---: |
| 24 | 16,777,216 | 268,435,456 | 6 GiB |
| 25 | 33,554,432 | 536,870,912 | 12 GiB |
| 26 | 67,108,864 | 1,073,741,824 | 24 GiB |

The edge-record size is 24 bytes; these are input sizes, not runtime memory
estimates. Execution needs additional adjacency, vertex state, buffers and
possibly a transpose. Undirected adjacency can expand each tuple to two arcs.
Parquet compression and runtime memory depend on the graph and execution path.

Graph-data buffers grow with the selected chunk sizes, not the total edge
count; the manifest's file metadata grows with the number of partitions.
The C generator keeps one chunk of packed edges, float32 weights and
24-byte output records. Python checks and writes one chunk at a time. No global
duplicate count or isolate count is computed. Larger chunks reduce the number
of Parquet files but require more temporary memory.

Without `--reference`, the manifest explicitly records
`validation.status = "reference-not-generated"`. Retain this status until a
separate scalable correctness check has completed. Preparing a large input is
not evidence that a traversal implementation ran correctly on it.

## Identity, files and reproducibility

Each successful directory contains:

- `vertices.parquet/part-*.parquet`: all `id: int64` values.
- `edges.parquet/part-*.parquet`: `src: int64`, `dst: int64`, `weight: float64`.
- `reference.parquet`: optional `id`, `bfs`, `sssp`; unreachable distances are null.
- `manifest.json`: parameters, counts, build receipt, converter identity,
  preparation timing, library versions, thread environment and every Parquet
  file's SHA256 and byte count.
- `preparation.json` and `generator.stderr`: launch receipt and diagnostics.

`canonical.edges.sha256` hashes the little-endian `(int64 src, int64 dst, float64
weight)` stream in generator order. It stays constant when conversion chunk
sizes change. Parquet file hashes need not: partitioning, compression libraries
and PyArrow versions can affect them. `canonical.vertices.sha256` similarly
hashes the ascending little-endian int64 vertex IDs. To require an existing
canonical input identity during reproduction, pass
`--expected-edge-sha256 <canonical.edges.sha256>`.

The output directory must not exist. Failed conversion leaves diagnostics,
partial files and `failure.json`, without a success manifest; it never silently
overwrites or resumes a previous preparation. Keep failure evidence and use a
new output directory for a retry.

Run converter and real-generator tests, including exact equality across chunk
sizes:

```bash
GRAPH500_SOURCE="$GRAPH500_WORK/upstream" \
  "$GRAPH500_WORK/venv/bin/python" -m pytest -q \
  examples/extensions/benchmarks/test_graph500_fixture.py
```

Before comparing with external controls, match topology, directedness, duplicate
policy, source and weights. The pinned GAPBS and Parallel-SSSP controls use
integer edge-weight types in their existing drivers. Rounding these floating
weights would define a different SSSP workload and must not be reported as an
equivalent run. See [the traversal plan](TRAVERSAL-PLAN.md) for control pins and
the separate Sail-call and kernel-only measurement boundaries.

## Run a single certified Sail trial

After building the traversal branch and its wheels with the
[traversal tutorial](TRAVERSAL-TUTORIAL.md), use a fresh Linux container for each
measured trial. The following paths must exist inside that container:

```bash
.venv/bin/python examples/extensions/benchmarks/graph_cell.py \
  --sail-binary /absolute/path/sail \
  --runtime-source-sha "$REVIEW_SOURCE_SHA" \
  --native-source-sha "$REVIEW_SOURCE_SHA" \
  --dataset /absolute/path/scale10 --output /absolute/path/new-bfs-cell \
  --engine nutmeg-native --algorithm bfs --variant push_pull \
  --source 0 --no-directed --mode process-cluster \
  --traversal-validation certificate --certificate-max-rounds 10000 \
  --max-iterations 1000 --timeout 1800
```

Select `--algorithm sssp --variant delta_star --delta 0.1` for the new native
weighted kernel, or change the engine to `pecan` or `nutmeg-datafusion` for the
relational path. For a functional run outside a private Linux container, add
`--allow-unisolated`; those observations are not publishable benchmark timings.
The default per-process pool/quota still needs to fit the intended host envelope.
Begin with scale10 before a capacity pilot. A capacity refusal, timeout, or
certificate cap is retained as its actual outcome, never a completed benchmark.

## Run the complete matrix

Copy [graph500-matrix.example.json](graph500-matrix.example.json) outside the
checkout and replace the machine paths, image and three exact source commits.
Build the pinned generator **inside the Linux environment** and place it with
its build receipt at the configured `datasets.scale10.generator` path in the
mounted target volume. A macOS generator cannot run inside a Linux container.

```bash
python examples/extensions/benchmarks/run_matrix.py \
  --config /absolute/path/graph500-config.json --dry-run
python examples/extensions/benchmarks/run_matrix.py \
  --config /absolute/path/graph500-config.json --prepare-only
python examples/extensions/benchmarks/run_matrix.py \
  --config /absolute/path/graph500-config.json --skip-prepare
```

The example runs all 36 combinations of local/process mode, Pecan/Banda/Grenada,
and the three methods for each algorithm. Every trial uses a fresh container;
generation runs separately before the trials. The dry run includes both
preparation and trial commands. All outcomes and cleanup records are retained.

For a larger input, set `scale` and `vertices = 2^scale`, then change the
dataset's `validation` to `"certificate"`. Large reference-oracle requests are
rejected before preparation. Optional `certificate_max_rounds` limits the
outside-timing certificate computation; exhausting it fails validation.
`expected_edge_sha256` can pin the canonical edge-stream hash from a previous
preparation across machines. Leave `source`, `directed`, seeds and edge factor
identical for every compared path. The matrix still uses a fixed source and
does not claim an official Graph500 run.
